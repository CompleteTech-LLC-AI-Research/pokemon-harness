## The #551 meta-path BLOCKER is still live — reproduced on `89e7305`

Independent review of `650a8bcc` returned REQUEST CHANGES with a BLOCKING finding: a custom
`sys.meta_path` finder can supply a foreign submodule *after* the guard returns PASS. I reproduced
it on the merged head rather than trusting the report, and it is still exploitable:

    guard status: PASS
    imported file: <tmp>/foreign/probe_pkg/leaked.py
    LEAKED_FOREIGN_AFTER_PASS: True
    VERDICT: BLOCKER_LIVE

Shape: a local `probe_pkg`, a foreign-only `probe_pkg/leaked.py`, and a `find_spec` that returns a
`spec_from_file_location` for `probe_pkg.leaked` from the foreign tree. `check_origins(local,
("probe_pkg",))` reports PASS because the top-level origin and every `__path__` portion are local,
then `import probe_pkg.leaked` loads foreign code.

One caution for whoever fixes this: an early repro attempt appeared to show no leak. The cause was
a `target` name collision in the probe's own `find_spec` signature shadowing the closure variable
that held the foreign path — not any behaviour change in the guard. A regression test for this
vector must not make the same mistake, or it will pass vacuously.

**#551 is therefore not mergeable on content regardless of CI.** This sync only brings it onto
current trunk; it does not address the blocker. A separate fix must make the guard fail closed on
installed/custom `sys.meta_path` finders that can intercept a checked package's submodules, while
preserving standard `PathFinder` behaviour.

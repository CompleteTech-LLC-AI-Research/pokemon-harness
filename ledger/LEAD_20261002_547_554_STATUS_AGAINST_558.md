## #547 — vacuous PASS on an empty package tuple

Issue #547 reports `check_origins()` returning `{"packages": [], "status":
"PASS"}` when called with `()` — `all()` over an empty sequence is `True`, so a
guard asked to verify nothing reports that everything is fine.

Measured on the #558 head:

```
>>> check_origins(root, ())
{'project_root': '...', 'packages': [], 'status': 'FAIL',
 'detail': 'no packages were selected to verify'}
```

**Fixed.** The guard now fails closed at the report boundary.

So #547 is **not** closed on trunk, and merging #551, #548 or #549 would land

This is the first *functional* difference between the branches, as opposed to
the defence-in-depth differences already recorded in

argument for consolidating onto #558 rather than repairing five branches.

**#547 stays open** — the repair is on an unmerged PR, and the PR is
unreviewed. Closing it before the merge would misreport the state.

## #554 — a non-editable wheel install is refused

Issue #554 reports that a wheel built from this checkout and installed
non-editably fails the guard, because pip's `direct_url.json` for a wheel
install names the **wheel file in the wheelhouse** rather than the source tree:

```
editable: {"url":"file:///.../checkout","dir_info":{"editable":true}}
wheel:    {"archive_info": {}, "url":"file:///.../house/pokered_harness-0.1.0-py3-none-any.whl"}
```

`_is_this_checkout` resolves neither `project_root` nor a staging directory
beneath it, so the distribution contributes no allowed root and the install is
refused.

**This is left open deliberately, and it is a decision, not a defect.** The
issue itself lays out three options and notes that #551 declined to decide
because widening `_is_this_checkout` to accept wheelhouse paths would make any
`.whl` on disk an allowed root — weakening the provenance guarantee #534
exists to provide.

I am not taking that decision unilaterally either. The narrow, honest position
is that the guard currently certifies editable and staged installs and
refuses wheel installs, and that this should be stated in the documented
release lane rather than left ambiguous.

Note the interaction with `run_local_ci.sh`, which builds a wheel into
`$RUNNER_TEMP/pokered-wheels` and installs it into a clean venv. That clean
venv check does **not** run the import-origin guard, so the refusal #554
describes does not currently fail local CI. That is why #534's AC4 can be
demonstrated in both directions without tripping over #554.

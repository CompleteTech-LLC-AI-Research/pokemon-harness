## The questions that decide whether this is safe

The hoist moves three reads out of a per-instruction loop. The only way that is a regression is if
one of `mb`, `cpu`, `lcd` can change identity *during* a single call to `_step_single_step_chunk`.

### Q1/Q2 — can `p.mb.lcd` or `p.mb` be rebound mid-loop?

**No.** The authoritative source is the vendored PyBoy's assembled runtime, not the facade. The
motherboard is generated from `vendor/pyboy-src/pyboy/core/mb_components/`, assembled by
`_pyboy_runtime.pxi` via `pyboy/_source.py`.

    mb_core_001_bffdd9436480.pxi:43      self.cpu = cpu.CPU(self)
    mb_core_001_bffdd9436480.pxi:45      self.lcd = lcd.LCD(

An exhaustive grep across every `.pxi` in the vendored package for a rebinding assignment finds
only those two lines, both inside `__init__`. There is no later `self.lcd = ...` or
`self.cpu = ...` anywhere — not in `mb.tick()`, not in `breakpoint_add/remove/reached/reinject`.

The breakpoint path is the one that looked risky, and it was checked directly: `breakpoint_add`
and `breakpoint_remove` write *memory contents* (`self.lcd.VRAM0[x] = OPCODE_BRK`,
`self.ram.internal_ram0[...] = opcode`). They mutate elements of objects held under `self.lcd`;
they never reassign `self.lcd`. Mutating `VRAM0[...]` is invisible to this method, which only reads
`frame_done`.

`frame_done` itself is set in `_pyboy_runtime.pxi:16` (`self.mb.lcd.frame_done = False`) and by the
LCD's own frame logic — attribute mutation on a stable object, which the hoisted reference reads
correctly.

Test doubles: every `.lcd = ` assignment in `tests/` is in a constructor
(`test_pyboy_link_session.py:36,817,849`, `test_stepping_loop_profile.py:460`). No double defines
`lcd` as a property, and none swaps it inside `tick()`. `_FrameBoundaryDouble.tick()` does
`self.lcd.frame_done = True` — mutation, not rebinding.

### Q3 — is the `getattr(cpu, "cycles", start_cycles)` default still reachable?

**Yes, unchanged.** `start_cycles = getattr(cpu, "cycles", None)` is evaluated once before the
loop in both versions, so `start_cycles is not None` iff `cpu` exposes `cycles`. The hoist hoisted
`cpu` — which the original had *already* hoisted (`cpu = getattr(p.mb, "cpu", None)` was above the
loop). So the per-iteration `getattr(cpu, "cycles", start_cycles)` reads exactly the same object in
both versions. The default fires only when `cpu` has no `cycles` attribute at all, and that path
was exercised (scenario 6 below).

### Q4 — can a stale `lcd` clear `frame_done` on the wrong object or leave PyBoy stopped?

**No**, by Q1: the object cannot differ. The probe's `stop_on_frame=False consumes frame_done`
scenario confirms identical resulting `frame_done` state and identical final cycles.

### Q5 — the `return bool(getattr(lcd, ...))` line

This is a real behavioural *difference*, in the safe direction, and it is worth recording
precisely. In the original, `lcd` was bound only inside the loop body, so if the loop never
executed the final `return bool(getattr(lcd, "frame_done", False))` would raise `UnboundLocalError`.
The hoisted version cannot raise, because `lcd` is bound before the loop.

Can the loop be skipped? **No.** `fallback_ticks = max(1, cycle_budget // 7)` is `>= 1` for every
integer `cycle_budget`, and `max_ticks = min(max(fallback_ticks, cycle_budget * 4), 4096)` is
therefore `>= 1`. Verified exhaustively for budgets `-100, -5, 0, 1, 2, 6, 7, 100`: `max_ticks` is
`1, 1, 1, 4, 8, 24, 28, 400` — always positive.

So this is an unreachable-in-practice latent bug that the hoist removes, not a behaviour anyone
can observe. It does not change any passing test.

### Q6 — does the 1.495x survive scrutiny?

> **NO — this answer was wrong, and it is retracted.** I wrote "plausible and not confounded."
> Later review established the opposite, and my reasoning above contains a specific error:
> I treated `p.mb.lcd` as one of the three per-instruction `getattr` calls. It is not — `p.mb.lcd`
> is an *attribute access*. Only `getattr(p.mb, "lcd", None)` was ever a `getattr` call.

Corrected, measured by shadowing `builtins.getattr` and counting calls directly:

| arm | getattr per retired instruction |
|---|---|
| original | 3.0007 |
| hoisted | 2.0010 |
| **delta** | **exactly 1.0** |

So the hoist removes one `getattr` per instruction, not three. The real effect is about **1.11x** on
an isolated stub loop, and on a real motherboard it is not resolvable against host noise (1.064x
and 0.959x on separate runs). See `ledger/FINDING_581_HOIST_SPEEDUP_NOT_REPRODUCED_20261004.md`.

Two parts of my original answer survive: the identical retired-instruction and cycle counts were
real and do prove no emulated work was skipped, and the "a 10x claim would have been the suspicious
number" instinct pointed the right way — the number was suspicious, just not by the mechanism I
gave. The lesson is narrower than "trust the number": **the `getattr` count I used came from
`cProfile`, which during re-verification reported 0 calls in both arms.** A profiler that reports
zero cannot support any per-call claim, and I did not check that before building an argument on it.
### Q7 — anything else

`ticks` accounting, the stall guard, cancellation, hook firing and partial-progress accounting are
untouched: the diff moves reads and changes only the spelling of `p.mb` to `mb`. `ticks += 1`,
the `start_cycles` compare, the `fallback_ticks` break, and the hook branch are all byte-identical.

## Executable differential probe

Both implementations, verbatim, run against identical configurable fake motherboards. Compared
return value, final cycles, `frame_done`, `breakpoint_singlestep`, `breakpoint_singlestep_latch`,
hooks fired, tick count, and breakpoints removed.

| scenario | match |
|---|---|
| basic `stop_on_frame`, frame in middle | OK |
| no frame boundary, budget exhausted by cycles | OK |
| `stop_on_frame=False` consumes `frame_done` | OK |
| `frame_done` pre-set, returns True immediately | OK |
| breakpoint fires once, hooks handled | OK |
| `cpu` has **no** `cycles` attr (fallback path) | OK |
| `mb` has **no** `lcd` attr | OK |
| tiny budget (1 cycle) | OK |
| zero budget | OK |

**All 9 match.** The two "attribute missing" scenarios are the ones that matter most, because they
are the cases where hoisting could plausibly have dropped a `getattr` default.

## Verdict

**No behavioural regression found.** The specific mechanism that would have made this unsafe —
identity change of `mb`/`cpu`/`lcd` mid-loop — is ruled out by exhaustive source grep over the
authoritative assembled runtime, and the observable behaviour is shown identical by executable
differential probe across nine scenarios including both missing-attribute fallbacks.

Disposition: **this does not clear #581 for merge.** The merge contract requires an independent
*agent* review, which remains unobtainable while #489 is live. #581 stays a draft PR.

The outstanding quiet-CPU re-measurement is **withdrawn as a plan**: a later run established the
1.495x figure is wrong (~1.11x, and not resolvable on a real motherboard), so re-measuring the
original number is not worth doing. The docstring and commit message were corrected to the measured
figure and its scope in `5e8c23c8`. The correctness verdict above is unaffected.
